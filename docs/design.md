# 设计与实施次序

选择 Python + Playwright 持久化 Chromium 窗口和 CLI。其他选择是接管已有浏览器（需要远程调试配置，容易和日常浏览冲突），或按屏幕坐标点击（窗口位置和缩放影响可靠性）。用户已明确要求直接实施首选方案。

状态流：WAITING → SENDING → WAITING_RESPONSE → COMPLETED；异常为 FAILED，任务为 PAUSED。点击前持久化 click_intent；已记录意图的步骤恢复后只能核对，不能再次点击。用户消息必须等于发送前完整列表加当前 prompt，且输入框清空。历史指纹不同、额外用户输入、DOM 不完整时不推断发送成功。

回答必须新增 assistant 消息，保留旧历史指纹，没有生成/忙碌状态，输入框可用且空，网络在线，没有错误，有本轮回复操作按钮，最后消息及全部 assistant 指纹连续稳定。页面刷新/异常/离线会清空稳定计时。网页 DOM 不是服务端协议，因此不能证明数学意义的 exactly-once，也不能保证网站改版后识别仍有效；不确定时停下。

Phase 1：浏览器适配和完成检测，使用本地模拟页面验证。
Phase 2：串行任务执行，验证上一轮完成前不发送下一轮。
Phase 3：严格配置解析、跨天调度、即时运行。
Phase 4：准备阶段重试、观察恢复、截图日志、超时。
Phase 5：原子断点写入、系统锁、配置指纹、故障恢复测试。
Phase 6：外置提示词、逐步等待参数、模型只读记录、Windows 提示音。

测试采用 Python 自带 unittest（无需额外测试框架）；pytest 更简洁但多一个依赖；只手动测试难以重复覆盖崩溃窗口，因此选择 unittest 加本地 Playwright 页面验证。

安全取舍：不自动点击 Retry/重新生成，因为此操作可能生成第二个回答分支。retry_count 控制发送前准备和报错后的观察恢复次数，绝不将其作为不确定发送的重发次数。网络恢复后自动重新读取 DOM，登录由用户手动处理。超时后允许继续也必须先安全排空当前回答；仍无法确认就暂停。

第一版不支持接管普通 Chrome 已开的标签，不切换模型，不处理深度研究需要用户中途确认的交互，不自动导出下载附件。桌面通知未实现；完成提醒使用控制台和 Windows 提示音。

## 桌面版与连接模式扩展

用户确认原生 Windows 桌面窗口方案，采用 Python 自带 Tkinter。Tk 主线程仅处理表单和事件队列；单独工作线程持有 asyncio 循环和 Playwright，CLI/GUI 共用 app/runtime.py。停止只取消一次任务并等待清理，避免第二次取消中断浏览器关闭；运行时锁定编辑。

配置保存先校验、保留 .bak、再原子替换。TXT 未修改保留文件引用，编辑后转为内联 prompt，原文件不改动。中文编号分步只识别另起一行的连续标题，代码围栏内容不拆分，导入先预览。

用户报告手动人机验证循环后，增加连接已开启本机 CDP 端口的普通 Chrome/Edge 模式。CDP 是浏览器提供的控制协议，不是验证码绕过。辅助按钮启动独立配置目录、127.0.0.1 端口的安装版浏览器，用户先手动登录。连接时只选择唯一已打开目标标签，断开时停止 Playwright 客户端，不关闭对方 context 或 browser。旧专用窗口模式继续可用。
